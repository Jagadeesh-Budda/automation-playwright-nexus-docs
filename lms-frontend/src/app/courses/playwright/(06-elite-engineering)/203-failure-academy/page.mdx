## The Nature of Flakiness

A "flaky" test is a test that sometimes passes and sometimes fails without any code changes. In an enterprise environment, **flakiness is a systemic poison**. If developers stop trusting the test suite, they will start ignoring failures, defeating the entire purpose of automation.

### Root Causes of Failure

<Tabs>
  <Tab title="1. Race Conditions">
    The test executes an action (like clicking "Save") and immediately tries to assert the result before the network request finishes processing.
    
    **Fix**: Rely on Web-First Assertions (`toBeVisible()`) which automatically poll until the condition is met or the timeout is reached.
  </Tab>
  <Tab title="2. Data Pollution">
    Test A creates a record. Test B attempts to create the same record but fails because it already exists. 
    
    **Fix**: Ensure perfect isolation using dynamic data generation (Faker) and rigorous `afterEach` cleanup.
  </Tab>
  <Tab title="3. Environment Drift">
    The Staging environment is updated with a new configuration that differs from the Development environment, causing selectors to vanish or behave differently.
    
    **Fix**: Implement robust locators (`getByRole`) that depend on the accessibility tree, not arbitrary CSS classes.
  </Tab>
</Tabs>

## The Debugging Arsenal

When a test fails in CI/CD, you cannot simply "watch" it run. You must rely on telemetry.

1. **Trace Viewer**: The most powerful tool. It records every network request, DOM snapshot, console log, and action. You can "time travel" through the test execution to see exactly what the browser saw.
2. **Screenshots & Videos**: Capture the visual state precisely when the test crashed.
3. **Playwright Inspector**: Best used locally to step through execution line-by-line.

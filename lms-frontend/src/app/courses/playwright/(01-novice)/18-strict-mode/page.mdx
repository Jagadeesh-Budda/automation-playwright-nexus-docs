## The "Strict Mode" Violation

Playwright operates in **Strict Mode**. This is one of its most important features.

Strict Mode means: **If you ask Playwright to click an element, and it finds MORE THAN ONE matching element, it will instantly crash the test.**

```typescript
// Imagine a page with two "Submit" buttons (one at the top, one at the bottom)
await page.getByRole('button', { name: 'Submit' }).click(); 
// ❌ CRASH: strict mode violation
```

### Why does it crash?

Older frameworks would just silently click the *first* button they found. 

But what if the developer added a hidden "Submit" button at the very top of the HTML? Your test would silently start clicking the wrong button, and you wouldn't know until the test failed much later with a confusing error.

Playwright forces you to be explicit. If there are two buttons, you must tell Playwright exactly which one you mean.

### How to fix a Strict Mode Violation

1. **Be more specific:** Can you use `getByRole` with a different name?
2. **Filter by parent:** Find the section of the page first, then find the button inside it.

```typescript
// Find the footer first, then the submit button inside the footer
const footer = page.getByRole('contentinfo'); // HTML5 footer role
await footer.getByRole('button', { name: 'Submit' }).click();
```

3. **Use `.first()` or `.nth()`:** Only if the elements are truly identical lists (as covered in the last lesson).

## Debugging: `page.pause()`

When your test fails, and the error message isn't enough, you need to see what the browser is seeing.

You can freeze time by adding `await page.pause()` to your test:

```typescript
import { test, expect } from '@playwright/test';

test('debug my test', async ({ page }) => {
  await page.goto('https://playwright.dev');
  
  // Freeze the test here!
  await page.pause(); 
  
  await page.getByRole('button', { name: 'Get started' }).click();
});
```

When you run this test (make sure you run it **headed** with `--headed`), the browser will open and completely pause. 

A tool called the **Playwright Inspector** will pop up. 
- You can explore the page in the browser.
- You can test new locators in the Inspector to see what they highlight.
- You can click the "Resume" button to let the test continue.

> [!IMPORTANT]
> Never commit `await page.pause()` to your codebase! It will cause your automated CI/CD pipeline to hang forever waiting for someone to click "Resume".

## UI Mode (The Ultimate Debugger)

There's an even better way to debug tests: **UI Mode**.

Instead of running `npx playwright test`, run:

```bash
npx playwright test --ui
```

This opens a dedicated dashboard where you can:
- See a list of all your tests.
- Click any test to run it visually.
- Scrub back and forth in time through every single click and network request.
- Inspect the DOM as it looked at *any* moment in the past.

Whenever you get stuck finding a locator, UI Mode is the best place to figure it out.

## Common Mistakes

- **Hardcoding Waits**: Using `page.waitForTimeout()` instead of waiting for an element's state.
- **Overly Broad Locators**: Using generic CSS selectors like `.button` that might break if multiple buttons are added. Always prefer user-facing attributes like `getByRole`.
- **Ignoring Errors**: Catching errors in try/catch blocks without failing the test or logging the reason.

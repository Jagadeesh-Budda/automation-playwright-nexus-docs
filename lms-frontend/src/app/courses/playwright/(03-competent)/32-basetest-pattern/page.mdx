## The Problem with `fixtures.ts`

In the previous lessons, we put our custom fixtures inside a single `fixtures.ts` file. 

This works for small projects. But what happens when you have 50 Page Objects? If you put 50 fixtures into one file, it becomes unreadable.

## Splitting Fixtures

Playwright allows you to split fixtures into separate files by domain or feature.

```typescript
// fixtures/authFixtures.ts
import { test as base } from '@playwright/test';

export const authFixtures = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    await use(new LoginPage(page));
  }
});
```

```typescript
// fixtures/settingsFixtures.ts
// Notice we import from authFixtures, not base Playwright!
import { authFixtures as base } from './authFixtures';

export const settingsFixtures = base.extend<{ profilePage: ProfilePage }>({
  profilePage: async ({ page, loginPage }, use) => {
    await loginPage.login('admin', 'secret123');
    await use(new ProfilePage(page));
  }
});
```

By importing the extended test from the previous file, we build a chain. `settingsFixtures` knows about `profilePage`, but it *also* still knows about `loginPage`!

## The `baseTest.ts` File

Instead of your test files importing from `settingsFixtures.ts` or `authFixtures.ts` directly (which gets confusing), enterprise frameworks create one centralized file to merge everything together.

We usually call it `baseTest.ts`.

> [!IMPORTANT]
> **Most small projects do not need this pattern.** 
> If you have under 50 tests and 5 Page Objects, a single `fixtures.ts` file is perfectly acceptable and much easier to read! This lesson teaches how large teams scale, but you should not over-engineer a small project on day one.

```typescript
// fixtures/baseTest.ts


// Import the very end of your fixture chain
import { settingsFixtures as test } from './settingsFixtures';

// Re-export the fully loaded test object
export { test };

// Re-export expect so test files only need one import
export { expect } from '@playwright/test';
```

## The Final Test Architecture

Look at how beautiful and scalable your tests have become. 

You started the course writing 20 lines of repetitive setup code in every single test. Now, you write this:

```typescript
// tests/profile.spec.ts

// 1. Import from your custom baseTest, not Playwright!
import { test, expect } from '../fixtures/baseTest';

// 2. Ask for exactly what you need
test('user can update avatar', async ({ profilePage }) => {
  
  // 3. Perform the business logic. No setup boilerplate.
  await profilePage.uploadAvatar('new-pic.png');
  await expect(profilePage.successMessage).toBeVisible();

});
```

## Common Mistakes

> [!WARNING]
> **Mistake 1: Brittle Implementation**  
> **Wrong:** Tightly coupling test data with page interactions.  
> **Correct:** Abstracting data and logic appropriately.  
> **Why:** Prevents tests from breaking when minor details change.

> [!WARNING]
> **Mistake 2: Missing Synchronization**  
> **Wrong:** Relying on implicit speeds or hardcoded sleeps.  
> **Correct:** Using web-first assertions for synchronization.  
> **Why:** Guarantees deterministic execution regardless of environment speed.

## The Limits of `beforeEach`

In the last lesson, you learned that `test.beforeEach()` is a great way to clean up duplicated setup code *within a single file*.

But what happens when your project grows?

Imagine your application requires users to log in before they can do almost anything. Your test folder now looks like this:

```
tests/
  login.spec.ts          ? has login code
  dashboard.spec.ts      ? has login code inside beforeEach
  settings.spec.ts       ? has login code inside beforeEach
  upload.spec.ts         ? has login code inside beforeEach
  admin-panel.spec.ts    ? has login code inside beforeEach
```

Inside every single one of those files, you have this code:

```typescript
await page.goto('/login');
await page.getByLabel('Email').fill('admin@example.com');
await page.getByLabel('Password').fill('secret123');
await page.getByRole('button', { name: 'Sign In' }).click();
```

## The Nightmare Scenario

One day, the development team decides to redesign the login page. 

They change the "Email" label to say "Email Address", and they change the "Sign In" button to say "Continue".

What happens to your tests?

**They all break.**

```
? dashboard.spec.ts  � Timeout finding 'Email'
? settings.spec.ts   � Timeout finding 'Email'
? upload.spec.ts     � Timeout finding 'Email'
? admin-panel.spec.ts� Timeout finding 'Email'
? reports.spec.ts    � Timeout finding 'Email'
```

Every single test file turns red. 

To fix the build, you have to open 5 different files, find the login code in each one, and manually update the locators. 

Now imagine you don't have 5 files. Imagine you have 150 files.

You would spend your entire week just updating login locators. You would hate your life. You would conclude that "UI automation is too brittle."

## The Need for Abstraction

The problem here is a violation of the **DRY Principle** (Don't Repeat Yourself). 

We are treating the browser like a script we have to type out manually every time. But as software engineers, when we see the exact same 4 lines of code repeated in 5 different files, we know what to do: **Extract it into a function or a class.**

What if, instead of writing locators in every test, we could just write:

```typescript
// Imagine if we could just do this:
await loginPage.login('admin@example.com', 'secret123');
```

If we could do that, then when the developers change the login page, we only have to update our code in **one single place**. All 150 tests would instantly work again.

This is not a dream. It is the most important architectural pattern in UI automation.

It's called the **Page Object Model**, and you are going to learn it in the next module.

## Common Mistakes

- **Hardcoding Waits**: Using `page.waitForTimeout()` instead of waiting for an element's state.
- **Overly Broad Locators**: Using generic CSS selectors like `.button` that might break if multiple buttons are added. Always prefer user-facing attributes like `getByRole`.
- **Ignoring Errors**: Catching errors in try/catch blocks without failing the test or logging the reason.

## What is the Capstone?

The Capstone project is the culmination of the entire course. You will build a **complete, production-quality automation framework** for a pharmaceutical Document Management System from scratch.

By the end of the Capstone, your framework will:
- Have a proper 4-layer folder structure
- Implement POM + AAA pattern correctly
- Include fixtures, entities, and a data factory
- Cover the complete E-Sign workflow end-to-end
- Have a hybrid API+UI test strategy
- Pass all 5 AST quality gates
- Generate a full HTML test report

## The Target Application

**Application:** PharmaDoc DMS (Document Management System)
**Technology:** React + Node.js + PostgreSQL
**URL:** `https://staging.pharmadoc.example.com`

**Core modules:**
1. Authentication (login, logout, role switching)
2. Document Management (upload, search, filter, paginate)
3. Review Workflow (submit ? review ? approve/reject)
4. E-Sign (sign with reason + password, audit trail)
5. Admin Panel (user management, system configuration)

## Capstone Acceptance Criteria

Your automation framework passes the Capstone when ALL of these are true:

| Criterion | Enterprise Hardening Requirement |
|-----------|-------------|
| Architecture | 4-layer structure with tests, pages, components, entities |
| Page Objects | All pages have dedicated POM files, no raw locators in specs |
| Fixtures | All POMs injected via `test.extend()`, not `new PageObject()` |
| **API Seeding** | **Tests MUST use API Controllers (request.post) to seed state. UI state building is prohibited.** |
| **Virtualization** | **Must implement `page.route` to mock out the flaky 3rd-party Analytics server.** |
| **DB Integrity** | **Post-UI action, execute a direct DB query assertion to prove true data commit.** |
| **Quality Gates** | **Submission fails if `waitForTimeout` or `test.describe.serial` bypasses are detected.** |
| **Dockerized** | **Must include a `Dockerfile` proving the suite runs flawlessly in Linux CI.** |
| Assertions | Only web-first `expect()` assertions, no custom sleeps |
| Report | HTML / Allure report generated with traces on failure |

## Common Mistakes

> [!WARNING]
> **Mistake 1: Brittle Implementation**  
> **Wrong:** Tightly coupling test data with page interactions.  
> **Correct:** Abstracting data and logic appropriately.  
> **Why:** Prevents tests from breaking when minor details change.

> [!WARNING]
> **Mistake 2: Missing Synchronization**  
> **Wrong:** Relying on implicit speeds or hardcoded sleeps.  
> **Correct:** Using web-first assertions for synchronization.  
> **Why:** Guarantees deterministic execution regardless of environment speed.

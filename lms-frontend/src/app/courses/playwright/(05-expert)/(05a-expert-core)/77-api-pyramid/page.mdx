## The Test Pyramid

The Test Pyramid is a framework for balancing your test investment. It tells you how many tests to write at each level.

```
         /\
        /  \
       / UI \        ? Few (10-20%) — Slow, expensive, high coverage
      /------\
     / API    \      ? More (30-40%) — Fast, reliable, targeted
    /----------\
   / Unit       \    ? Most (50-60%) — Blazing fast, isolated
  /--------------\
```

**Why not write everything as a UI test?**
- UI tests take 10-60 seconds each
- UI tests break when the design changes
- UI tests depend on the full stack (browser + app + database)

**The sweet spot:** Use API tests for complex business logic, and UI tests only to verify the user experience.

## Playwright's API Testing Capability

Playwright has a built-in HTTP client (`request`) that lets you make direct API calls — no browser, no UI, pure HTTP.

```typescript
import { test, expect } from '@playwright/test';

// This test runs without opening any browser — just raw HTTP
test('GET /api/documents returns paginated results', async ({ request }) => {
  const response = await request.get('/api/documents', {
    params: { page: 1, limit: 10 }
  });
  
  expect(response.status()).toBe(200);
  
  const body = await response.json();
  expect(body.data).toHaveLength(10);
  expect(body.pagination.total).toBeGreaterThan(0);
  expect(body.pagination.page).toBe(1);
});
```

## When to Use API Tests vs UI Tests

| Scenario | API Test | UI Test |
|----------|----------|---------|
| Business logic validation | ? Best | Too slow |
| Data validation (field types, formats) | ? Best | Fragile |
| Authentication/Authorization | ? Best | Too slow |
| Error handling (400, 401, 403, 500) | ? Best | Hard to trigger |
| Happy path user journey | ?? Partial | ? Best |
| Visual layout verification | ? Not possible | ? Only option |
| Cross-browser compatibility | ? Not possible | ? Only option |

## The Hybrid Strategy

The most efficient test suites use **both layers strategically**:

```typescript
import { test, expect } from '@playwright/test';

// Use API to set up state FAST, then UI to verify the user experience
test('approved documents appear in the approved list', async ({ request, page }) => {
  // Step 1: Create and approve a document via API (fast!)
  const createResponse = await request.post('/api/documents', {
    data: { title: 'Test Protocol', type: 'Protocol' }
  });
  const { id } = await createResponse.json();
  
  await request.post(`/api/documents/${id}/approve`, {
    headers: { Authorization: `Bearer ${process.env.ADMIN_TOKEN}` }
  });
  
  // Step 2: Verify the UI shows it correctly (can't do this via API)
  await page.goto('/documents?status=approved');
  await expect(page.getByRole('row').filter({ hasText: 'Test Protocol' })).toBeVisible();
});
```

## The `apiRequest` Context

Configure the global API request context:

```typescript
// playwright.config.ts
use: {
  // Base URL for all API requests
  baseURL: process.env.BASE_URL,
  
  // Default headers sent with every API request
  extraHTTPHeaders: {
    'Accept': 'application/json',
    'x-api-version': '2.0',
  },
}
```

## Common Mistakes

> [!WARNING]
> **Mistake 1: Brittle Implementation**  
> **Wrong:** Tightly coupling test data with page interactions.  
> **Correct:** Abstracting data and logic appropriately.  
> **Why:** Prevents tests from breaking when minor details change.

> [!WARNING]
> **Mistake 2: Missing Synchronization**  
> **Wrong:** Relying on implicit speeds or hardcoded sleeps.  
> **Correct:** Using web-first assertions for synchronization.  
> **Why:** Guarantees deterministic execution regardless of environment speed.

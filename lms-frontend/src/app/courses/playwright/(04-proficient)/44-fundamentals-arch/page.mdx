## Why Folder Structure Matters

A bad folder structure makes a test suite feel like a junk drawer — everything is mixed together, nothing is reusable, and new engineers can't find anything. A good folder structure makes the suite feel like a well-organized factory.

The ANA standard uses a **4-layer architecture** that maps directly to how a software application is built.

## The 4-Layer Architecture

```
project-root/
+-- tests/              ? LAYER 1: Test Specs (the "What")
¦   +-- admin/
¦   ¦   +-- login.spec.ts
¦   ¦   +-- document-upload.spec.ts
¦   +-- e-sign/
¦       +-- signature-flow.spec.ts
¦
+-- pages/              ? LAYER 2: Page Objects (the "How")
¦   +-- LoginPage.ts
¦   +-- DocumentPage.ts
¦   +-- ESignPage.ts
¦
+-- components/         ? LAYER 3: Reusable UI Components
¦   +-- Header.ts
¦   +-- Modal.ts
¦   +-- DataTable.ts
¦
+-- entities/           ? LAYER 4: Data Models & Types
¦   +-- User.ts
¦   +-- Document.ts
¦   +-- Signature.ts
¦
+-- fixtures/           ? Test infrastructure (base test, hooks)
¦   +-- baseTest.ts
¦
+-- utils/              ? Shared utility functions
¦   +-- dateHelper.ts
¦   +-- fileHelper.ts
¦
+-- data/               ? Test data (JSON, CSV, factories)
¦   +-- testUsers.json
¦
+-- .env                ? Secret config (never commit!)
+-- playwright.config.ts
+-- package.json
```

## Layer-by-Layer Explanation

### Layer 1: `tests/` — Test Specs (The "What")
These files contain **only** the test logic. They describe what you are testing in plain business language. They should be readable by a non-engineer.

<CodeExplainer preset="admin-login-spec" />

### Layer 2: `pages/` — Page Objects (The "How")
These files contain all the **selectors and interactions** for a specific page. When the UI changes, you only update this file — not 50 different test files.

<CodeExplainer preset="login-page-ts" />

### Layer 3: `components/` — Reusable UI Components
These model **shared UI elements** that appear on multiple pages (headers, modals, navigation, data tables).

<CodeExplainer preset="modal-ts" />

### Layer 4: `entities/` — Data Models & Types
These are TypeScript interfaces that define the **shape of your data**.

<CodeExplainer preset="user-ts" />

## The Golden Rule

| In `tests/` | Never... |
|------------|----------|
| Write selectors (`page.locator('#btn')`) directly | ? Use Page Objects instead |
| Hardcode URLs | ? Use `process.env.BASE_URL` |
| Import directly from `pages/` without a fixture | ? Use `baseTest` fixtures |

> [!TIP]
> If you find yourself copying and pasting a locator into two different spec files, it belongs in a Page Object. Always refactor before the duplication spreads.

## Common Mistakes

- **Hardcoding Waits**: Using `page.waitForTimeout()` instead of waiting for an element's state.
- **Overly Broad Locators**: Using generic CSS selectors like `.button` that might break if multiple buttons are added. Always prefer user-facing attributes like `getByRole`.
- **Ignoring Errors**: Catching errors in try/catch blocks without failing the test or logging the reason.

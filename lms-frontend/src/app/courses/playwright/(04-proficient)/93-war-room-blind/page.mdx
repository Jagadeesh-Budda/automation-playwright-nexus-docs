## Challenge A: The Silent Race Condition

**Bug Report from CI:** *"Test passes locally 100% of the time. Fails in CI ~35% of the time. Error: `Expected 'Upload successful' but received null.`"*

```typescript
import { test, expect } from '@playwright/test';

test.describe('Document Upload', () => {
  test('user uploads a PDF and sees confirmation', async ({ page }) => {
    await page.goto('/documents');
    await page.getByRole('button', { name: 'Upload' }).click();
    await page.locator('input[type="file"]').setInputFiles('report.pdf');
    await page.getByRole('button', { name: 'Confirm' }).click();
    const message = await page.locator('.toast-message').textContent();
    expect(message).toBe('Upload successful');
  });
});
```

<details>
<summary>🔎 Root Cause Analysis (try to find it yourself first!)</summary>

**Root Cause:** `.textContent()` is NOT a web-first assertion. It grabs the text content *immediately* — before the toast notification has rendered in the DOM.

On a fast local machine, the toast appears in ~50ms, so `.textContent()` grabs it in time. On a slow CI machine with limited resources, the toast takes ~200-500ms, so `.textContent()` returns `null`.

**The Fix:**
```typescript
import { test, expect } from '@playwright/test';

test('user uploads a PDF and sees confirmation', async ({ page }) => {
  await page.goto('/documents');
  await page.getByRole('button', { name: 'Upload' }).click();
  await page.locator('input[type="file"]').setInputFiles('report.pdf');
  await page.getByRole('button', { name: 'Confirm' }).click();
  // ✅ Web-first assertion — automatically retries until the toast appears
  await expect(page.locator('.toast-message')).toHaveText('Upload successful');
});
```

**Key Lesson:** Never use `.textContent()` or `.innerText()` as substitutes for assertions. Use `expect().toHaveText()` or `expect().toContainText()` — they retry automatically.

</details>

## Challenge B: The Data Collision

**Bug Report from CI:** *"Test passes when run individually. Fails when full suite runs with `--workers=4`. Error on test 2: `Expected row to be visible but it was not found.`"*

```typescript
import { test, expect } from '@playwright/test';

const testUser = {
  email: 'qa-test@company.com',
  name: 'QA Test User'
};

test('admin creates a user', async ({ page }) => {
  await page.goto('/admin/users');
  await page.getByRole('button', { name: 'Add User' }).click();
  await page.getByLabel('Email').fill(testUser.email);
  await page.getByLabel('Name').fill(testUser.name);
  await page.getByRole('button', { name: 'Save' }).click();
  await expect(page.getByText('User created')).toBeVisible();
});

test('admin searches for the user', async ({ page }) => {
  await page.goto('/admin/users');
  await page.getByRole('searchbox').fill(testUser.email);
  await expect(page.getByRole('row', { name: testUser.email })).toBeVisible();
});
```

### Your Task

1. Identify ALL the bugs (there are at least 3).
2. Write the corrected version.
3. Explain in comments why each issue causes failures.

<details>
<summary>🔎 Root Cause Analysis (try to find it yourself first!)</summary>

**Root Cause 1: Hardcoded email.**
`'qa-test@company.com'` is used by every test run. When Worker 1 creates this user and Worker 3 tries to create the same user simultaneously, the database rejects the duplicate email. On the second run, the user already exists from the first run.

**Root Cause 2: Test 2 depends on Test 1.**
The "search" test assumes the "create" test ran first and succeeded. In parallel, Worker 1 might run "search" while Worker 2 hasn't finished "create" yet. Even sequentially, if "create" fails, "search" fails too — masking the real error.

**Root Cause 3: No cleanup.**
The test creates data but never deletes it. After the first run, `qa-test@company.com` exists in the database permanently, causing "create" to fail on every subsequent run.

**The Fix:**
```typescript
import { test, expect } from '@playwright/test';

test('admin creates a user', async ({ page, request }) => {
  // ✅ Unique email per test run
  let uniqueEmail = `qa-test-${Date.now()}@company.com`;

  await page.goto('/admin/users');
  await page.getByRole('button', { name: 'Add User' }).click();
  await page.getByLabel('Email').fill(uniqueEmail);
  await page.getByLabel('Name').fill('QA Test User');
  await page.getByRole('button', { name: 'Save' }).click();
  await expect(page.getByText('User created')).toBeVisible();

  // ✅ Cleanup: delete the user after the test
  await request.delete(`/api/users?email=${uniqueEmail}`);
});

test('admin searches for the user', async ({ page, request }) => {
  // ✅ Atomic: create its OWN data via API
  const uniqueEmail = `search-test-${Date.now()}@company.com`;
  await request.post('/api/users', {
    data: { email: uniqueEmail, name: 'Search Test User' }
  });

  await page.goto('/admin/users');
  await page.getByRole('searchbox').fill(uniqueEmail);
  await expect(page.getByRole('row', { name: uniqueEmail })).toBeVisible();

  // ✅ Cleanup
  await request.delete(`/api/users?email=${uniqueEmail}`);
});
```

**Key Lessons:**
- Every test must create its own data (atomic isolation)
- Use dynamic identifiers (`Date.now()`, `crypto.randomUUID()`) to prevent collisions
- Always clean up test data in teardown

</details>

## Challenge C: The Environment Phantom

**Bug Report from CI:** *"Test passes in the morning. Fails every night at midnight. Error: `Expected number to be greater than 0 but received 0.`"*

```typescript
import { test, expect } from '@playwright/test';

test('verify document count on dashboard', async ({ page }) => {
  await page.goto('/dashboard');
  await page.waitForLoadState('networkidle');
  const count = await page.getByTestId('doc-count').textContent();
  expect(Number(count)).toBeGreaterThan(0);
});
```

### Your Task

This is the hardest challenge. The bug is NOT just a code issue — it's a combination of code AND environment.

1. Identify all the code-level issues.
2. Identify the environment-level issue.
3. Explain why it passes in the morning but fails at midnight.

<details>
<summary>🔎 Root Cause Analysis (try to find it yourself first!)</summary>

**Code Issue 1: `networkidle` is unreliable.**
`waitForLoadState('networkidle')` waits for 500ms of no network activity. If the dashboard has a WebSocket connection, a polling heartbeat, or analytics pings, `networkidle` may never resolve — or resolve prematurely.

**Code Issue 2: `.textContent()` is not a web-first assertion.**
Same pattern as Challenge A — `.textContent()` grabs the value immediately without retrying. If the dashboard count loads asynchronously after the page shell renders, it may still show "0" or an empty string.

**Environment Issue: Nightly database cleanup.**
The staging environment runs a scheduled job at midnight that wipes test data. In the morning, manual testers or other automated suites have created documents, so the count is > 0. At midnight, the cleanup runs, leaving the count at 0. This is NOT a bug — the test is asserting on environment state it doesn't control.

**The Fix:**
```typescript
import { test, expect } from '@playwright/test';

test('verify document count on dashboard', async ({ page, request }) => {
  // ✅ Ensure at least one document exists (atomic data setup)
  await request.post('/api/documents', {
    data: { title: `Dashboard Test ${Date.now()}`, type: 'Protocol' }
  });

  await page.goto('/dashboard');

  // ✅ Web-first assertion with retry — no networkidle needed
  await expect(page.getByTestId('doc-count')).not.toHaveText('0');
});
```

**Key Lessons:**
- Never assert on data you didn't create yourself
- `networkidle` is almost never the right wait strategy
- Midnight failures = environment state issue, not code issue
- Always seed your own test data

</details>

## Common Mistakes

> [!WARNING]
> **Mistake 1: Brittle Implementation**  
> **Wrong:** Tightly coupling test data with page interactions.  
> **Correct:** Abstracting data and logic appropriately.  
> **Why:** Prevents tests from breaking when minor details change.

> [!WARNING]
> **Mistake 2: Missing Synchronization**  
> **Wrong:** Relying on implicit speeds or hardcoded sleeps.  
> **Correct:** Using web-first assertions for synchronization.  
> **Why:** Guarantees deterministic execution regardless of environment speed.
